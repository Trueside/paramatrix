# Параматрица — Architecture 0.3.1
## Content Infrastructure & State System

**Статус:** согласованная архитектурная спецификация  
**Основано на:** Architecture 0.3  
**Область:** Content Infrastructure, Entity Registry, State Definitions, State System, State Mutation API

---

## 1. Архитектурные инварианты

1. Logical State — единственный источник истины о состоянии игрового мира.
2. Static Definitions неизменяемы после регистрации.
3. Runtime State отделён от Definitions.
4. Unity Representation не владеет логическим состоянием.
5. Все runtime-изменения состояния проходят через State System.
6. State System не определяет сюжетные последствия.
7. Сценарные изменения инициируются Scenario System.
8. State Changed публикуется только после успешного commit.
9. Initialization и Restore не вызывают обычные игровые триггеры.
10. State System не содержит произвольной игровой логики.

## 2. Content Infrastructure

### 2.1. Pipeline

```text
JSON Files
    ↓
Content Loader
    ↓
JSON Parsing
    ↓
Structural Validation
    ↓
Content Validator
    ↓
Entity Registry
    ↓
Gameplay Systems
```

Gameplay Systems не загружают JSON самостоятельно.

### 2.2. Entity Registry

Registry хранит immutable definitions.

Концептуальный API:

```text
GetDefinition(entityId)
TryGetDefinition(entityId)
Exists(entityId)
GetDefinitionsByType(entityType)
```

Registry не хранит runtime State.

### 2.3. Entity ID

Предлагаемый формат:

```text
<entity_type>.<entity_name>
```

Примеры:

```text
character.paranoik
character.morpheus
item.red_pill
object.office_door
location.office
story.morpheus_meeting
```

Правила:

- lowercase Latin;
- цифры и underscore допустимы;
- точка отделяет тип сущности от имени;
- ID стабилен;
- ID не зависит от display name или Unity GameObject name.

Unity объекты регистрируются по стабильным ID. Запрещено использовать имена GameObject как логические идентификаторы.

## 3. Ownership State

State property принадлежит сущности, которую описывает его смысл.

| Тип состояния | Owner |
|---|---|
| Свойство персонажа | Character |
| Свойство предмета | Item |
| Свойство интерактивного объекта | Object |
| Свойство локации | Location |
| Сюжетная веха | Story entity |
| Технический статус сценарного Event | Scenario runtime |

### 3.1. Сюжетные факты

Если факт описывает отдельную сюжетную веху, он хранится у story-сущности.

Пример:

```text
story.morpheus_meeting.occurred
```

Не следует дублировать один факт в нескольких сущностях:

```text
character.paranoik.met_morpheus
character.morpheus.met_paranoik
story.morpheus_meeting.occurred
```

Если все три выражают один и тот же факт, источником истины должен быть один из них.

### 3.2. Различие Story State и Event State

Story State выражает смысловой факт:

```text
story.morpheus_meeting.occurred = true
```

Event State выражает технический факт исполнения сценария:

```text
event.morpheus_intro.completed = true
```

Они могут быть связаны сценарием, но не являются автоматически эквивалентными.

### 3.3. Не всякая сюжетная деталь требует Story Entity

Story Entity вводится для значимой сюжетной вехи, которую необходимо независимо проверять, сохранять или использовать в нескольких местах.

Не следует создавать отдельную сущность для каждого незначительного действия.

## 4. State Definitions

State Definition объявляет:

- owner;
- property;
- type;
- default value;
- persistence policy;
- constraints;
- mutation policy.

Пример:

```json
{
  "id": "story.morpheus_meeting",
  "states": {
    "occurred": {
      "type": "boolean",
      "default": false,
      "persistence": "persistent",
      "mutation_policy": "scenario_only"
    }
  }
}
```

Это пример структуры, не финальная JSON Schema.

### 4.1. State Address

State property адресуется парой:

```text
Entity ID + Property
```

Пример:

```text
entity = object.office_door
property = open
```

Полный логический адрес:

```text
object.office_door.open
```

Произвольные вложенные state trees в MVP не вводятся.

### 4.2. Типы

Поддерживаемые типы:

- Boolean;
- Integer;
- String;
- Enum.

Для Integer допускаются min/max.

Для Enum допустимые значения объявляются заранее.

### 4.3. Persistence

```text
persistent
transient
reconstructible
```

- `persistent` — сохраняется в Save;
- `transient` — существует только в текущем runtime;
- `reconstructible` — может быть восстановлено из других логических фактов.

Unity visuals не должны сохраняться как State.

### 4.4. Mutation Policy

Предлагаемые значения:

```text
scenario_only
system_only
scenario_or_system
```

- `scenario_only` — изменяется Scenario System;
- `system_only` — изменяется техническими игровыми системами;
- `scenario_or_system` — допускаются оба типа инициатора.

Это минимальная policy-модель для MVP. ACL и произвольные permissions не вводятся.

Initialization и Restore являются специальными операциями и не считаются обычными gameplay mutations.

## 5. State System

### 5.1. Responsibilities

State System отвечает за:

- runtime state storage;
- чтение State;
- проверку mutation requests;
- фиксацию изменений;
- публикацию State Changed;
- экспорт persistent state;
- восстановление snapshot.

State System не отвечает за:

- сюжетные решения;
- Condition evaluation;
- запуск Events;
- UI;
- Unity visuals;
- сохранение файла на диск.

### 5.2. Conceptual API

```text
GetState(entityId, property)
TryGetState(entityId, property)

SetState(entityId, property, value, source)

ExportPersistentState()
RestoreState(snapshot)
```

Названия и сигнатуры концептуальные. Финальный C# API будет определён при реализации.

### 5.3. Mutation Request

```text
SetState(
    entityId,
    property,
    value,
    source
) -> MutationResult
```

Параметры:

- `entityId` — ID сущности;
- `property` — property name;
- `value` — типизированное значение;
- `source` — контролируемый тип источника.

### 5.4. Mutation Sources

```text
Scenario
System
Initialization
Restore
```

`source` предназначен для контроля политики и диагностики. Он не должен быть произвольной строкой.

### 5.5. Mutation Result

```text
Applied
Unchanged
Rejected
```

`Rejected` сопровождается diagnostic code.

Предлагаемые коды:

```text
UnknownEntity
UnknownProperty
TypeMismatch
OutOfRange
InvalidEnumValue
MutationNotAllowed
```

Ошибки корректности данных должны дополнительно обнаруживаться Content Validator до запуска игры.

### 5.6. Повторная установка значения

Если новое значение совпадает с текущим:

```text
SetState(open, true)
```

при текущем:

```text
open = true
```

Результат:

```text
Unchanged
```

При этом:

- состояние не изменяется;
- State Changed не публикуется;
- сценарные триггеры повторно не запускаются.

### 5.7. Mutation Validation

Перед commit State System проверяет:

1. Entity существует.
2. Property существует.
3. Тип значения корректен.
4. Ограничения соблюдены.
5. Enum value допустим.
6. Mutation policy разрешает источник.

Если проверка не пройдена, изменение не производится.

### 5.8. Atomicity

Одна мутация атомарна:

- либо значение изменяется полностью;
- либо состояние остаётся прежним.

Batch transactions и rollback произвольной последовательности mutations не входят в MVP.

## 6. State Changed Notification

После успешного commit State System публикует уведомление:

```text
StateChanged
```

Payload:

```text
entityId
property
oldValue
newValue
source
```

### 6.1. Notification Rules

- Публикуется только после commit.
- Не публикуется при `Rejected`.
- Не публикуется при `Unchanged`.
- Не является источником истины.
- Получатели могут читать актуальный State через State System.

### 6.2. Scenario Integration

```text
Mutation Request
    ↓
State System validates
    ↓
State System commits
    ↓
State Changed notification
    ↓
Scenario System evaluates triggers
    ↓
Condition System evaluates conditions
    ↓
Event starts or is queued
```

State System не вызывает Scenario System напрямую внутри `SetState`.

Scenario System обрабатывает notifications в рамках своего event-processing cycle, чтобы избежать неконтролируемой рекурсии.

---

## 7. Initialization

Предлагаемый порядок:

```text
1. Load Content
2. Parse Definitions
3. Validate Definitions
4. Build Entity Registry
5. Build State Definitions Registry
6. Initialize State System
7. Initialize default State values
8. Initialize Gameplay Systems
9. Load initial Location
10. Register Unity Representations
11. Reconstruct visuals
12. Initialize Scenario System
13. Game Flow enters Free Roam
```

Initialization не запускает обычные сюжетные триггеры.

Visual reconstruction не считается сюжетной мутацией.

---

## 8. Restore

Restore — отдельная операция, не обычная последовательность `SetState`.

```text
RestoreState(snapshot)
```

Restore:

- проверяет snapshot;
- восстанавливает допустимые State values;
- не публикует обычные gameplay State Changed notifications;
- не запускает сценарные триггеры;
- не выполняет сюжетные действия.

После Restore системы реконструируют Unity Representation из восстановленного Logical State.

---

## 9. Save Integration

Save System получает данные через:

```text
ExportPersistentState()
```

Save System не собирает State напрямую из Unity GameObjects или отдельных Gameplay Systems.

State System отвечает за корректную выборку persistent properties.

---

## 10. Content Validator

Validator должен проверять:

- уникальность Entity IDs;
- существование owner;
- уникальность properties внутри owner;
- допустимые State types;
- корректность default values;
- min/max;
- Enum values;
- persistence policy;
- mutation policy;
- ссылки на сущности;
- неизвестные поля;
- обязательные поля.

Критические ошибки блокируют запуск. Warnings не блокируют запуск.

Автоматическое исправление произвольных ошибок не предусматривается.

---

## 11. Testing

### Content Infrastructure

- загрузка definitions;
- duplicate IDs;
- неизвестные references;
- корректность Registry;
- immutable definitions.

### State System

- чтение State;
- изменение State;
- неизвестный entity;
- неизвестный property;
- type mismatch;
- min/max;
- invalid Enum;
- mutation policy;
- Applied / Unchanged / Rejected;
- notification только после commit;
- атомарность одиночной mutation;
- persistent export;
- restore;
- отсутствие игровых triggers при restore.

### Integration

- Scenario инициирует сюжетную mutation;
- System инициирует техническую mutation;
- Condition System читает State;
- State Changed запускает trigger evaluation;
- Unity visuals реконструируются после изменения и загрузки.

---

## 12. Out of Scope

Не вводить в MVP:

- arbitrary transactions;
- rollback цепочек событий;
- произвольные mutation callbacks;
- пользовательские expressions;
- сложную ACL;
- автоматические side effects у properties;
- дублирование сюжетных фактов;
- сериализацию Unity Components;
- универсальный State framework для других игр.

---

## 13. Architectural Acceptance Criteria

Architecture 0.3.1 считается реализованной, когда:

1. Definitions загружаются централизованно.
2. Registry предоставляет immutable definitions.
3. Runtime State хранится отдельно.
4. State mutations проходят через State System.
5. Mutation policy соблюдается.
6. MutationResult корректно различает Applied, Unchanged и Rejected.
7. State Changed публикуется только после commit.
8. Scenario System получает notifications вне прямого вызова SetState.
9. Restore не запускает обычные сюжетные triggers.
10. Unity Representation восстанавливается из Logical State.
11. Save System получает persistent State через State System.
12. Validator обнаруживает ошибки definitions до запуска.

**Architecture 0.3.1 не фиксирует финальные C# signatures и JSON Schema.** Они будут определены после проверки Condition System и последующих gameplay contracts.
