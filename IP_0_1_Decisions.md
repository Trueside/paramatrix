# Параматрица — решения по вопросам Implementation Plan 0.1

Журнал решений пользователя по вопросам из `IP_0_1_Implementation_Plan.md` (Часть I).
После завершения разбора решения вносятся в план.

## Р0. Сквозной принцип: явная ошибка вместо подстраховки

Если что-то не работает, игра явно сообщает об ошибке. Неработающие сценарии не пропускаются, не перезапускаются,
не заменяются поведением «по умолчанию»: это скрывает проблему. Упор — на точность исполнения.

Все выборы вида «строгая ошибка / мягкий обход» решаются по этому принципу без отдельного согласования.

## Р1 (A1). Память о пройденных сценах и сюжетные факты

- Условия (Conditions) не проверяют статус сцен (Events) напрямую. Они проверяют только факты в State.
- Сцена, которая устанавливает сюжетно значимый факт, ставит его явно Action `set_state`.
- Факт хранится у сущности, к которой он относится по смыслу (свойство двери — у двери, встреча — у героя или у story-сущности).
- Постоянные факты не удаляются и не сбрасываются.
- Одноразовые «новости» (то, что герой должен донести) — отдельные свойства; их сбрасывает сцена, которая их использовала. Автоматической передачи фактов между персонажами нет.
- История выполнения сцен (once, once_per_location_visit) — внутреннее состояние Scenario System; сохраняется собственным снимком Scenario. Save = снимок State + снимок Scenario (уточнение 0.3.1 §9).

## Р2 (A2). Начало новой игры и загрузка

- New Game: после инициализации всех систем, включая Scenario, Game Flow выполняет обычный вход в стартовую локацию: начинается Visit #1, публикуется `LocationEntered`. Вступление — обычная сцена на `LocationEntered` с Launch Condition.
- Load Game: Restore State и Scenario, локация загружается технически, `LocationEntered` нет, новый Visit не начинается.
- Меняет порядок шагов 0.3.1 §7 (вход в стартовую локацию — после шага 12).

## Р3 (A3). Сцена, завершившаяся ошибкой

- Failed-сцена заблокирована: новые triggers её не запускают до загрузки сохранения.
- Статус Failed не сохраняется в снимок Scenario; после Load сцена снова доступна (с учётом её Repeat Policy).
- Автоматического повтора нет; запросы этой сцены в очереди удаляются.
- Уже применённые изменения State не откатываются (Addendum §3).
- Следствие для Gameplay Systems: штатные игровые помехи (путь перегорожен и т.п.) не должны возвращать Failure — их система обрабатывает сама (ждёт, обходит). Failure — только настоящая ошибка, иначе случайность блокирует сцену до загрузки.

## Р4 (A4). CALL и START недоступной сцены

- CALL и START проверяют у целевой сцены: не Running, не Failed, Repeat Policy, Launch Conditions.
- Любая проверка не пройдена (включая Launch Conditions = False) — Failure вызывающей сцены. Пропусков нет.
- Если вызов допустим не всегда, сценарист явно оборачивает его в `if`.

## Решения по принципу Р0 и по минимальности (без отдельного вопроса; возражения — до внесения в план)

- **A10. Один trigger — несколько сцен.** Кандидаты обрабатываются в порядке Event ID.
  Автоматический trigger: допустимые Exclusive встают в очередь в этом порядке (несколько сцен на «вход в офис» — нормально).
  Действие игрока: если допустимы две и более Exclusive — Error, не запускается ни одна. Validator предупреждает о пересечениях заранее.
- **A15. Save не совпадает с контентом** (удалено свойство, сменился тип, вышло за диапазон) — Load отклоняется целиком с ошибкой, мир не меняется. Миграции — вне MVP.
- **Предохранитель цепочек** (сцены бесконечно запускают друг друга) — Error, каскад останавливается.
- **Монитор ConditionsMet**, условие которого вычисляется с ошибкой, — Error diagnostic; срабатывания нет.
- **A9. `reconstructible`** — убирается из MVP: у него нет ни одного потребителя и нет правила восстановления. Остаются `persistent` и `transient`.
- **A11. Trigger types.** В MVP: Interaction, ItemAcquired, ItemUsed, ItemCombined, StateChanged, LocationEntered, DialogueCompleted, EventCompleted, ConditionsMet. PlayerAction, DialogueStarted, AnimationCompleted не реализуются, пока не определены; ссылка на них в контенте — ошибка Validator.
- **A16. Ссылка на сущность в State** (например, текущая локация) — Enum со значениями-ID; значение, не являющееся существующим ID, — ошибка Validator.

## Р6. Реакции на взаимодействия (0.3 §2.5, §5.6)

- Простые реакции — отдельный вид контента `response.*`: реплика без действий, не сцена.
- Порядок разрешения действия игрока: сначала сцены (Events), подходящие под действие; если ни одной — реакции по уровням specific → contextual → generic → fallback.
- Две и более подходящих сцены или две и более реакции одного уровня specific/contextual — Error (Р0).
- Generic — пул: реакции идут по кругу, одна и та же не повторяется подряд; пул из одной реакции — ошибка Validator.
- Fallback — ровно одна на каждый тип взаимодействия (Validator). «Нет реакции» допускается только явным объявлением.
- Реакцию, которой нужны действия (анимация и т.п.), оформляют сценой.

## Р7. Взять предмет, выйти из локации — только сценой

- Перемещение предмета (взять, отдать, израсходовать) и переход между локациями выполняются только Actions сцены. Inventory и Location System исполняют команды, сами решений не принимают.
- Нет сцены для действия — работает реакция (Р6), обычно fallback.

## Р8. Вид игры

- 2D, вид сбоку.

## Р9. Позиция героя после загрузки

- После Load герой появляется на точке входа локации по умолчанию. Позиция героя не сохраняется.

## Принято ранее, совпадает с рекомендацией (подтвердить)

- **A5.** Exclusive → START Exclusive: сцена встаёт в очередь и запускается после текущей цепочки.
- **A6.** Background-сцена выполняется мгновенно, ничего не ждёт; асинхронный Action в Background — ошибка Validator.
- **A7/A8.** Асинхронные Actions (dialogue, move, animation, transition) всегда ждут завершения; отдельного `wait` нет. Конец списка Actions — успешное завершение; `end` — досрочное.
