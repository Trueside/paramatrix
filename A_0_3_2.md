# Параматрица — Architecture 0.3.2
## Condition System

**Статус:** архитектурная спецификация  
**Основано на:** Architecture 0.3.1  
**Область:** Condition Definitions, Condition Evaluation, Scenario Integration

---

## 1. Назначение

Condition System предоставляет единый механизм вычисления логических условий игрового мира.

Она отвечает на вопросы:

- выполнено ли условие;
- соответствует ли State заданному значению;
- выполнена ли комбинация условий.

Condition System не определяет, когда проверять условие и что делать после проверки.

### Архитектурные инварианты

1. Condition System — единственная система вычисления истинности игровых условий.
2. Conditions не изменяют State.
3. Conditions не запускают Events.
4. Conditions не обращаются напрямую к Unity Representation.
5. Conditions не содержат произвольных expressions или C#.
6. Condition System не хранит копии State.
7. Результат зависит только от Definition и текущего Logical State.
8. Condition System не отвечает за расписание вычислений.

---

## 2. Типы Conditions

### 2.1. Atomic Condition

Проверяет одно State property.

Концептуальная структура:

```json
{
  "target": "object.office_door",
  "property": "open",
  "operator": "equals",
  "value": true
}
```

Atomic Condition содержит:

- target entity;
- property;
- operator;
- comparison value.

Condition System читает State через State System.

### 2.2. Compound Condition

Объединяет несколько Conditions.

Поддерживаемые операторы:

```text
all
any
not
```

Пример:

```json
{
  "all": [
    {
      "target": "object.office_door",
      "property": "open",
      "operator": "equals",
      "value": true
    },
    {
      "target": "story.morpheus_meeting",
      "property": "occurred",
      "operator": "equals",
      "value": true
    }
  ]
}
```

### 2.3. Named Condition

Named Condition имеет стабильный ID и может использоваться несколькими Events.

Пример:

```text
condition.can_enter_morpheus_room
```

Named Condition — immutable Definition.

Она не хранит вычисленный результат и не имеет собственного runtime State.

---

## 3. Operators

| Operator | Семантика |
|---|---|
| `equals` | Значения равны |
| `not_equals` | Значения не равны |
| `greater_than` | Больше |
| `greater_or_equal` | Больше или равно |
| `less_than` | Меньше |
| `less_or_equal` | Меньше или равно |

### Type Rules

- `equals` и `not_equals` допускаются для совместимых типов.
- Numeric operators допускаются для Integer.
- Enum сравнивается по объявленному значению.
- Неявное преобразование типов запрещено.
- String не сравнивается численно.
- Boolean не поддерживает numeric operators.

Validator проверяет совместимость типов.

Condition System не преобразует `"1"` в `1` или `true` в `1`.

---

## 4. Condition Evaluation

### 4.1. Conceptual API

```text
Evaluate(conditionId) -> ConditionResult

Evaluate(conditionDefinition) -> ConditionResult
```

Это концептуальный API, не финальная C#-сигнатура.

### 4.2. Condition Result

```text
True
False
Error
```

Семантика:

- `True` — условие корректно и выполнено;
- `False` — условие корректно, но не выполнено;
- `Error` — условие невозможно корректно вычислить.

Error не является False.

### 4.3. Возможные Errors

```text
UnknownCondition
UnknownEntity
UnknownProperty
TypeMismatch
InvalidOperator
InvalidDefinition
ConditionCycle
```

Runtime Error сопровождается диагностикой.

Condition Error не должен запускать Event.

Validator должен обнаруживать большинство таких ошибок до запуска игры.

### 4.4. Compound Evaluation

Правила:

- `all` истинно, если все дочерние Conditions истинны;
- `any` истинно, если хотя бы одно дочернее Condition истинно;
- `not` инвертирует True и False;
- Error распространяется через Compound Condition.

Предлагается не скрывать Error за False или True в Compound Conditions.

Для MVP размеры Condition trees невелики, поэтому предпочтительнее корректная диагностика, а не оптимизация short-circuit evaluation.

### 4.5. Empty Compound Conditions

Пустые `all`, `any` и `not` запрещены.

Validator должен сообщать об ошибке.

---

## 5. Condition References

Named Conditions могут ссылаться на другие Named Conditions.

Пример:

```text
condition.can_enter_room
    ↓
condition.door_open
    ↓
condition.office_power_on
```

Это позволяет переиспользовать общую логику.

### Ограничения

- циклические ссылки запрещены;
- неизвестные Condition IDs запрещены;
- ссылки проверяются Validator;
- Conditions не могут ссылаться на Events;
- Conditions не могут запускать Actions;
- Conditions не могут изменять State.

Validator проверяет циклы в графе Condition references.

---

## 6. Condition System и State System

Condition System читает State исключительно через State System.

```text
Condition System
       ↓
State System
       ↓
Logical State
```

Condition System не обращается напрямую к:

- Inventory System;
- Interaction System;
- Location System;
- Game Flow;
- Unity GameObjects.

Если факт представлен в Logical State, Condition System должна иметь возможность проверить его без обращения к gameplay systems.

---

## 7. Condition System и Scenario System

Condition System вычисляет условия по запросу.

Scenario System определяет, когда выполнять Evaluate.

Примеры:

- перед запуском Event;
- при выборе Dialogue option;
- при проверке Interaction;
- после State Changed;
- при входе в Location;
- при проверке Event trigger.

Scenario System не реализует собственные условия.

Все проверки выполняются через Condition System.

### 7.1. Event Launch Conditions

Event может иметь Launch Conditions.

Перед запуском:

```text
Event Triggered
    ↓
Evaluate Launch Conditions
    ↓
True → Event may start
False → Event does not start
Error → Event does not start; diagnostic
```

Launch Conditions не являются частью Event Action Sequence.

### 7.2. Action Conditions

Отдельные Actions могут иметь Conditions.

Пример:

```text
IF condition.door_is_locked
    → Start Dialogue
ELSE
    → Open Door
```

Scenario System определяет последовательность действий, Condition System — только истинность условия.

---

## 8. Conditions Met Trigger

Condition System не отслеживает изменения условий самостоятельно.

Наблюдение реализуется на стороне Scenario System.

### 8.1. State Changed Integration

```text
State System
    ↓
State Changed
    ↓
Scenario System
    ↓
Reevaluate relevant monitored Conditions
    ↓
Condition false → true?
    ↓
Trigger Event
```

Condition System не подписывается на State Changed и не хранит наблюдателей.

### 8.2. Edge Semantics

`Conditions Met` означает переход:

```text
false → true
```

Условие, которое уже истинно при регистрации наблюдения, не запускает Event автоматически.

Это предотвращает повторные срабатывания при initialization и restore.

Если требуется проверить уже истинное условие при входе в Location, используется `Location Entered` trigger с Launch Conditions.

### 8.3. Monitoring State

Runtime-значение предыдущего результата условия принадлежит Scenario System.

Condition System не хранит:

- previous result;
- trigger history;
- Event state;
- monitor registration.

### 8.4. Repeatable Events

Для repeatable Event:

- `false → true` может запускать Event;
- `true → true` не запускает повторно;
- после перехода `true → false` Event может быть снова активирован при следующем `false → true`.

Ограничения Event execution, включая `once`, `repeatable` и `once_per_location_visit`, остаются ответственностью Scenario System.

---

## 9. Initialization и Restore

Condition System не запускает Events при initialization.

Scenario System при регистрации monitors:

1. вычисляет текущие Conditions;
2. устанавливает baseline;
3. начинает отслеживать дальнейшие изменения.

Restore не генерирует обычные State Changed notifications.

После Restore Scenario System восстанавливает monitor baseline из текущего State.

Это предотвращает ложные `false → true` transitions во время загрузки.

---

## 10. Validator

Validator проверяет:

- уникальность Named Condition IDs;
- существование targets;
- существование properties;
- корректность operators;
- совместимость типов;
- допустимость comparison values;
- корректность Compound Conditions;
- отсутствие пустых Conditions;
- отсутствие циклических references;
- отсутствие неизвестных fields;
- наличие обязательных fields.

Critical errors блокируют запуск.

Warnings не блокируют запуск.

## 11. Testing

### Atomic Conditions

- True;
- False;
- Equals;
- Not Equals;
- Integer comparisons;
- Enum comparison;
- Type mismatch;
- Unknown entity;
- Unknown property.

### Compound Conditions

- All;
- Any;
- Not;
- Nested combinations;
- Error propagation;
- Empty condition validation.

### Named Conditions

- Reference resolution;
- Reuse;
- Unknown reference;
- Circular reference detection.

### Integration

- Event Launch Conditions;
- Action Conditions;
- State Changed reevaluation;
- false → true trigger;
- true → true no trigger;
- true → false reset;
- Restore baseline;
- отсутствие false triggers при загрузке.

---

## 12. Out of Scope

Не вводить:

- произвольные expressions;
- scripting language;
- пользовательские operators;
- Conditions с side effects;
- Conditions, меняющие State;
- автоматический polling;
- Condition System scheduler;
- Condition System event dispatcher;
- сложную систему subscriptions;
- cached Condition results без доказанной необходимости.

---

## 13. Acceptance Criteria

Condition System считается реализованной, когда:

1. Atomic Conditions читают State через State System.
2. Compound Conditions работают корректно.
3. Named Conditions переиспользуются.
4. Validator обнаруживает некорректные references.
5. Condition Result различает True, False и Error.
6. Type mismatch не превращается в False.
7. Condition System не изменяет State.
8. Scenario System использует Condition System для всех сюжетных проверок.
9. Conditions Met trigger реагирует на false → true.
10. Restore не вызывает ложных Condition transitions.
11. Unity Representation не участвует в Condition evaluation.

**Финальные JSON Schema и C# interfaces будут определены после Scenario System, когда станут ясны все основные потребители Condition API.**
