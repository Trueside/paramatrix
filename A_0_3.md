# Параматрица — Architecture 0.3
## Architectural Context: Game Flow, Dialogue, Location, Inventory & Interaction

**Status:** Consolidated architectural notes  
**Purpose:** предоставить Claude Code ранее согласованные архитектурные решения для подготовки Implementation Plan.

**Важно:** документ представляет собой сводку решений из обсуждений. Он не является полным техническим контрактом и не предписывает конкретную C# реализацию.

Claude Code должен:
- использовать эти сведения при разработке Implementation Plan;
- выявлять отсутствующие контракты и технические ambiguities;
- не менять согласованную семантику без явного согласования;
- не начинать реализацию до отдельного разрешения.

---

# 1. Game Flow System

## 1.1. Responsibility

Game Flow System отвечает за:
- текущий игровой режим;
- разрешения игрока на действия;
- владение управлением;
- блокировки и причины блокировок;
- переходы между режимами;
- безопасное возвращение управления игроку.

Game Flow не является Scenario System.

Scenario System управляет последовательностью сценарных действий, но не должна самостоятельно управлять Unity Input System или напрямую изменять игровые input permissions.

Scenario System запрашивает у Game Flow Exclusive control.

## 1.2. Game Modes

Предусмотрены следующие режимы:

- Free Roam
- Exclusive Event
- Minimalistic Dialogue
- VN Dialogue
- Transition
- Loading / Recovery

Exclusive Event и Dialogue presentation mode — независимые измерения.

Exclusive Event может содержать:
- Minimalistic Dialogue;
- VN Dialogue;
- другие сценарные действия.

Dialogue mode не определяет, является ли сценарное событие Exclusive.

## 1.3. Control Ownership

Предусмотрены владельцы управления:

- Player
- Scenario
- System

Game Flow управляет передачей и освобождением контроля.

Не следует реализовывать универсальный глобальный флаг `isInputLocked`, поскольку блокировки могут иметь разные причины и владельцев.

Game Flow должен поддерживать безопасное возвращение управления после:
- успешного завершения Exclusive Event;
- ошибки Event;
- завершения Dialogue;
- Transition;
- Loading / Recovery.

При Event failure Scenario System освобождает Exclusive control, а Game Flow возвращается в безопасное состояние.

Конкретная реализация control ownership и input permissions определяется Implementation Plan.

# 2. Dialogue System

## 2.1. Responsibility

Dialogue System отвечает за отображение и воспроизведение диалога.

Он:
- показывает реплики;
- управляет последовательным продвижением по репликам;
- обрабатывает пользовательское подтверждение;
- сообщает о завершении Dialogue.

Dialogue System **не управляет сюжетной логикой** и не решает, какое сценарное действие выполнять после диалога.

Scenario System запускает Dialogue и ожидает его завершения.

## 2.2. Dialogue Modes

Поддерживаются два режима.

### Minimalistic Dialogue

- Реплики отображаются в минималистичных speech bubbles.
- Реплики идут последовательно.
- Игрок продвигает диалог кликом или Space.
- Герой неподвижен.
- Управление перемещением заблокировано.
- Допускаются ограниченные анимации мира.
- Автономное поведение NPC приостанавливается.
- Музыка и SFX продолжают воспроизводиться.
- Автоматического переключения в VN mode нет.

### VN Dialogue

- Мир и управление игроком приостанавливаются.
- Dialogue UI остаётся активным.
- Реплики идут последовательно.
- Продвижение выполняется игроком.
- Не предусмотрен skip всего диалога одним действием.

## 2.3. Scenario Integration

Scenario System:
1. запускает Dialogue;
2. ожидает `DialogueCompleted`;
3. продолжает выполнение Event.

Dialogue System не должен самостоятельно запускать следующие сюжетные Events.

Dialogue mode выбирается сценарным контентом.

Dialogue может быть линейным. Выборы игрока не являются обязательной функцией базовой системы и должны появляться только при наличии соответствующего авторского контента.

## 2.4. Completion and Cancellation

Dialogue completion и техническая отмена Dialogue — разные события.

Dialogue может быть отменён из-за:
- Loading;
- Transition;
- Recovery.

Техническая отмена не должна считаться успешным завершением Dialogue.

Диалог считается завершённым только при нормальном достижении конца.

## 2.5. Dialogue Reactions

Для реакций персонажей предусмотрен resolver:

1. специальная реакция для текущего State;
2. contextual reaction;
3. generic reaction pool;
4. отсутствие реакции.

Generic reactions:
- могут циклически использоваться;
- не должны повторяться непосредственно подряд.

Resolver относится к Dialogue/Scenario integration, а не к Dialogue Player.

Dialogue Player отображает выбранную реакцию, но не определяет сюжетные условия её выбора.

# 3. Location System

## 3.1. Responsibility

Location System отвечает за:
- загрузку и выгрузку игровых локаций;
- переходы между локациями;
- регистрацию Unity representations;
- связь логической локации с её Unity representation.

В игре одновременно активна одна Location.

Переходы между локациями мгновенные с точки зрения игрового процесса.

## 3.2. Unity Scene Structure

Предполагается следующая модель:

- Persistent Bootstrap Scene;
- отдельная Unity Scene для каждой Location.

Bootstrap Scene содержит persistent systems.

При переходе:
- текущая Location Scene выгружается;
- новая Location Scene загружается;
- persistent systems остаются активными.

Конкретная техническая реализация загрузки определяется Claude Code.

## 3.3. Logical Location vs Unity Scene

Unity Scene является визуальным и пространственным представлением Location.

Unity Scene не является источником истины о логическом состоянии мира.

Logical State сохраняется независимо от загрузки и выгрузки Location Scene.

Состояние объектов и персонажей не должно теряться при переходе между локациями.

Unity representations регистрируются по стабильным Entity IDs.

GameObjects и их имена не должны выступать в роли логических идентификаторов.

## 3.4. Location Entry

Scenario System получает Trigger `LocationEntered` при обычном игровом входе в локацию.

`LocationEntered` не возникает при:
- Restore;
- визуальной реконструкции;
- повторной регистрации Unity representations;
- технической перезагрузке Unity Scene без сюжетного перехода.

Restore и обычный вход в Location должны различаться.

Location Visit — runtime concept, принадлежащий Scenario System.

Обычный вход начинает новый Visit. Restore не должен создавать новый Visit.

# 4. Inventory System

## 4.1. Responsibility

Inventory System отвечает за:
- владение предметами;
- отображение Inventory UI;
- выбор предмета;
- применение предметов;
- операции с предметами.

Inventory System не является источником сюжетной логики.

Результат применения предмета определяется Scenario System и Logical State.

## 4.2. Item Model

Items уникальны.

Не поддерживаются:
- stacks;
- количества предметов;
- generated instance IDs;
- несколько экземпляров одного Item.

Предмет может принадлежать одному из следующих мест:

- `world`
- `inventory`
- `npc`
- `consumed`

Для `npc` указывается owner NPC ID.

Предмет одновременно может находиться только в одном месте.

Inventory хранит references на Items.

Ownership в Logical State является источником истины.

Положение предмета в мире может храниться отдельно от ownership.

## 4.3. Item State

Состояние предмета хранится в Logical State.

Inventory System не должна самостоятельно изменять State напрямую.

Изменения выполняются через State System и специализированные Gameplay Systems.

Scenario System управляет сюжетным результатом операций с предметами.

## 4.4. Inventory UI

Предусмотренное поведение:

- компактная иконка предмета;
- hover panel с дополнительной информацией;
- выбранный предмет остаётся закреплённым в UI;
- правый клик отменяет выбор;
- применение предмета к объекту может инициировать движение героя;
- применение предмета может сопровождаться анимацией;
- успешное применение может изменить State;
- Scenario System может очистить выбор предмета после успешного применения.

Конкретный layout и визуальный дизайн не являются частью архитектурного контракта.

## 4.5. Item Operations

Поддерживаются:
- Take;
- Use;
- Apply Item to Object;
- Combine Items.

При неудачном применении предмета к объекту выбранный предмет остаётся выбранным.

Успешное применение может очистить selection.

Сюжетные последствия операций определяются Scenario System, а не Inventory System.

# 5. Interaction System

## 5.1. Responsibility

Interaction System — единая точка маршрутизации взаимодействий игрока.

Она:
- определяет тип взаимодействия;
- формирует Interaction Context;
- передаёт запрос соответствующим Gameplay Systems;
- сообщает о результате взаимодействия.

Interaction System не содержит индивидуальную сюжетную логику каждого объекта.

## 5.2. Interaction Types

Предусмотрены следующие типы:

- `inspect`
- `primary`
- `take`
- `talk`
- `use`
- `apply_item`
- `combine_items`
- `exit`

## 5.3. Input Mapping

- Left Mouse Button — primary interaction.
- Right Mouse Button — inspect.
- Keyboard — movement.
- Selected Item + Target — apply item.
- Selected Item + Inventory Item — combine items.
- Right-click on empty area — cancel item selection.

Unity Input System используется для обработки ввода.

Interaction System не должна самостоятельно управлять Unity Input System.

## 5.4. Interaction Context

Interaction Context содержит:

- interaction type;
- target;
- item;
- source;
- location.

Context передаётся соответствующим системам и может использоваться Scenario System.

Trigger payload содержит контекст взаимодействия, а не копию Logical State.

## 5.5. Availability vs Outcome

Availability и Outcome — разные понятия.

Объект может быть доступен для взаимодействия, но взаимодействие может завершиться неудачей.

Пример: закрытая дверь остаётся интерактивной. Игрок может попытаться открыть её, получить реакцию или сообщение.

Locked object не должен просто исчезать из списка взаимодействий.

## 5.6. Interaction Resolution

Для определения реакции используется следующий порядок:

1. State-specific response;
2. Contextual response;
3. Generic response;
4. Fallback response.

Конкретные реакции должны быть представлены контентом.

Interaction System не должна содержать индивидуальную сюжетную логику объектов в C#.

## 5.7. Movement and Interaction

Unity representation отвечает за:
- hitboxes;
- spatial interaction;
- approach positioning;
- animations.

Логические определения объектов и взаимодействий находятся в JSON.

Scenario System определяет последовательность сюжетных действий.

Interaction System инициирует взаимодействие и передаёт контекст, но не реализует сюжетный Event.

## 5.8. Remote Interaction

Remote Interaction не является отдельной универсальной системой.

Удалённое взаимодействие допустимо только через специально предусмотренный игровой канал:

- phone;
- computer;
- radio;
- terminal;
- другой сюжетный communication device.

Прямое взаимодействие с удалёнными объектами без такого канала не поддерживается.

# 6. Cross-System Architectural Invariants

Следующие правила применяются ко всем перечисленным системам:

1. Logical State — единственный источник истины о состоянии игрового мира.
2. Unity representation отображает Logical State, но не владеет им.
3. Unity MonoBehaviours и UI не изменяют State напрямую.
4. Runtime State изменяется через State System.
5. Scenario System управляет сюжетной последовательностью.
6. Gameplay Systems реализуют специализированные игровые механики.
7. Scenario System не должна дублировать механику Inventory, Dialogue, Interaction или Location.
8. Unity GameObject names не являются логическими Entity IDs.
9. Restore не должен создавать обычные gameplay triggers.
10. Unity Scene loading не должно приводить к потере Logical State.
11. Dialogue и Event execution — разные сущности.
12. Exclusive control принадлежит Game Flow, а не Scenario System напрямую.
13. Сюжетные последствия взаимодействий определяются State и Scenario, а не индивидуальной логикой Unity objects.
