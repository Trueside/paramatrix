# Параматрица — Architecture 0.4
## Scenario System

**Статус:** архитектурная спецификация  
**Основано на:** Architecture 0.3.1 и 0.3.2  
**Область:** Triggers, Events, Actions, Execution, Event Flow, integration

---

## 1. Назначение

Scenario System управляет исполнением игровых сценариев.

Она отвечает за:

- обработку игровых triggers;
- определение возможности запуска Event;
- запуск и исполнение Event;
- управление последовательностью Actions;
- ожидание завершения игровых операций;
- координацию сценарных вызовов;
- управление Exclusive и Background Events;
- взаимодействие с Condition System;
- постановку Events в очередь;
- обработку сценарных ошибок.

Scenario System не реализует игровые механики самостоятельно.

Она использует специализированные Gameplay Systems.

### Архитектурные инварианты

1. Scenario System — единственный исполнитель сюжетных сценариев.
2. Condition System — единственная система вычисления Conditions.
3. State System — единственный источник Logical State.
4. Scenario System не содержит логики Inventory, Dialogue, Interaction или Location.
5. Scenario System инициирует игровые операции через соответствующие systems.
6. Unity MonoBehaviours не содержат сюжетной логики.
7. Scenario System не исполняет произвольный C#.
8. Scenario Definitions являются immutable.
9. Runtime Event execution отделён от Event Definition.
10. Один Event не может иметь одновременно несколько execution instances.

---

## 2. Основные сущности

Scenario System работает с четырьмя понятиями:

| Entity | Назначение |
|---|---|
| Trigger | Сообщает о потенциальном запуске Event |
| Event | Описывает сценарную последовательность |
| Condition | Проверяет возможность выполнения |
| Action | Выполняет действие или вызывает Gameplay System |

Trigger не является Event.

Condition не является Trigger.

Action не является Condition.

Event объединяет их в сценарную последовательность.

---

## 3. Trigger System

### 3.1. Назначение

Trigger сообщает Scenario System, что произошло событие, потенциально важное для сценария.

Trigger не гарантирует запуск Event.

После Trigger Scenario System проверяет:

- Event availability;
- Launch Conditions;
- Repeat Policy;
- Event execution state;
- текущие ограничения Game Flow.

### 3.2. Trigger Types

Для MVP предлагаются:

```text
PlayerAction
Interaction
ItemAcquired
ItemUsed
ItemCombined
StateChanged
LocationEntered
DialogueStarted
DialogueCompleted
AnimationCompleted
EventCompleted
ConditionsMet
```

### 3.3. Trigger Payload

Trigger должен содержать контекст произошедшего события.

Пример Interaction:

```text
triggerType = Interaction
interactionType = inspect
targetId = object.office_door
itemId = null
locationId = location.office
source = Player
```

Пример Item Used:

```text
triggerType = ItemUsed
itemId = item.red_pill
targetId = object.office_door
locationId = location.office
```

Trigger payload — информация о произошедшем действии, а не копия State.

Scenario System может прочитать актуальный State через State System.

### 3.4. Trigger Matching

Event может быть связан с одним или несколькими Trigger definitions.

Scenario System проверяет соответствие входящего Trigger Event definition.

Trigger matching — механическая фильтрация по типу и параметрам, не сюжетное условие.

Например:

```text
Trigger:
    type = Interaction
    target = object.office_door
    interaction = primary
```

Condition System не используется для проверки самого Trigger matching.

### 3.5. Trigger Delivery

Gameplay Systems публикуют Trigger notifications.

Scenario System принимает их и обрабатывает.

Scenario System не опрашивает Gameplay Systems каждый frame.

Для MVP не требуется универсальная event bus infrastructure. Достаточен централизованный механизм передачи trigger notifications.

## 4. Event Definition

Event Definition описывает сценарную последовательность.

Концептуальная структура:

```text
Event:
    id
    triggers
    launchConditions
    repeatPolicy
    executionType
    actions
```

Пример:

```text
event.morpheus_intro
```

### 4.1. Event ID

Event ID стабилен и не зависит от названия сцены, Unity GameObject или текста диалога.

### 4.2. Launch Conditions

Launch Conditions проверяются перед запуском Event.

Если Condition Result:

- `True` — Event может быть запущен;
- `False` — Event не запускается;
- `Error` — Event не запускается, ошибка диагностируется.

Launch Conditions не выполняются внутри Action Sequence.

### 4.3. Repeat Policy

```text
once
repeatable
once_per_location_visit
```

#### once

Event может успешно завершиться только один раз за прохождение.

#### repeatable

Event может запускаться повторно, если отсутствует другой execution conflict.

#### once_per_location_visit

Event может успешно завершиться один раз в рамках конкретного посещения Location.

Visit — отдельная runtime-концепция.

Location Visit начинается при обычном входе в Location.

Restore не создаёт новый Visit.

Event execution state и Visit state принадлежат Scenario System.

### 4.4. Поведение после ошибки

Предлагается:

- `once` фиксирует completion только после успешного завершения;
- `repeatable` может быть запущен повторно;
- `once_per_location_visit` фиксирует completion после успешного завершения в текущем Visit.

Failed Event не считается Completed.

---

## 5. Event Lifecycle

Event runtime states:

```text
Idle
Running
Completed
Failed
```

### Idle

Event не исполняется.

### Running

Event исполняется.

Повторный запрос запуска игнорируется.

### Completed

Event успешно завершён.

### Failed

Event завершился ошибкой исполнения.

Failed Event не считается Completed.

### 5.1. Lifecycle

```text
Idle
  ↓ Trigger
Launch Conditions
  ↓
Running
  ↓ Successful END
Completed
```

Если Launch Conditions не выполнены, Event остаётся Idle.

Если Event завершился ошибкой:

```text
Running → Failed
```

Failed Event не запускается автоматически повторно.

Повторный запуск допустим только через явный сценарный механизм или после recovery.

---

## 6. Event Execution Types

Для MVP:

```text
Exclusive
Background
```

### 6.1. Exclusive Event

Exclusive Event может:

- блокировать player input;
- запускать Dialogue;
- двигать героя;
- выполнять scripted movement;
- инициировать Location Transition;
- блокировать другие Exclusive Events;
- использовать WAIT;
- вызывать другие Events.

Одновременно может исполняться только один active Exclusive Event.

### 6.2. Background Event

Background Event предназначен для ограниченных фоновых операций.

Background Event не может:

- блокировать player input;
- запускать Dialogue;
- двигать героя;
- изменять Location;
- инициировать Transition;
- захватывать Game Flow;
- ждать завершения player-controlled Dialogue;
- выполнять длительные операции, требующие exclusive control.

Background Event может:

- изменять разрешённый State;
- выполнять простые Actions;
- вызывать другие Background Events;
- проверять Conditions;
- завершаться.

### 6.3. Ограничение Background State Mutations

Background Event не должен изменять State, который конфликтует с текущим Exclusive Event.

Для MVP не вводится сложная система locks.

Вместо этого:

- Background Actions ограничены;
- Conditions перепроверяются перед значимыми Actions;
- сценарист избегает конкурирующих изменений;
- Validator обнаруживает очевидные conflicts, но не гарантирует их полное отсутствие.

---

## 7. Exclusive Event Arbitration

### 7.1. Один active Exclusive Event

Если Exclusive Event уже выполняется, новый Exclusive Event не запускается немедленно.

### 7.2. Automatic Event Queue

Автоматические Exclusive Event requests помещаются в очередь.

Примеры источников:

- State Changed;
- Conditions Met;
- Event Completed;
- Location Entered.

Когда текущий Exclusive Event завершится:

1. Scenario System выбирает следующий queued request.
2. Повторно проверяет Event availability.
3. Повторно проверяет Launch Conditions.
4. Проверяет текущий Repeat Policy.
5. Запускает Event, если он всё ещё допустим.

Если Conditions больше не выполняются, request отменяется.

### 7.3. Player-initiated Events

Player-initiated Exclusive Event не должен автоматически превращаться в длинную очередь.

Если событие невозможно выполнить из-за текущего Exclusive Event, запрос отклоняется.

Это предотвращает ситуацию, когда игрок случайно ставит множество действий в очередь.

### 7.4. Queue Policy

Для MVP:

- FIFO;
- без priorities;
- без preemption;
- без автоматического прерывания;
- без сложной arbitration system.

Queued requests могут быть удалены при переходе в Loading, Recovery или другой технический режим.

---

## 8. Action System

Action — атомарная сценарная операция.

Action может:

- изменить State;
- вызвать Gameplay System;
- запустить Dialogue;
- выполнить Transition;
- вызвать Event;
- ожидать завершения операции;
- завершить Event.

### 8.1. Action Categories

```text
StateMutation
Dialogue
Movement
Animation
InventoryOperation
InteractionOperation
LocationTransition
CallEvent
StartEvent
Wait
If
Else
End
```

Список — архитектурный набор типов, а не обязательная структура JSON.

### 8.2. Action Execution

Scenario System:

1. выбирает Action;
2. вызывает соответствующую system;
3. получает результат;
4. при необходимости ожидает completion;
5. переходит к следующему Action.

Scenario System не реализует сами механики.

### 8.3. Action Result

Концептуальные результаты:

```text
Success
Failure
Pending
```

- `Success` — операция завершена;
- `Failure` — операция не выполнена;
- `Pending` — требуется ожидание.

Точные типы и C# interfaces определяются позднее.

### 8.4. State Mutation Action

Сюжетное изменение State выполняется через State System.

```text
Scenario Action
    ↓
State System.SetState(...)
    ↓
MutationResult
```

Scenario System не изменяет State напрямую.

---

## 9. Sequence Control

Для MVP поддерживаются:

```text
IF
ELSE
WAIT
CALL
START
END
```

### 9.1. IF / ELSE

IF использует Condition System.

```text
IF condition.door_is_locked
    Dialogue("door_locked")
ELSE
    Transition("office")
```

Condition Error приводит к ошибке Event, а не автоматически к ELSE.

ELSE соответствует False, но не Error.

### 9.2. WAIT

WAIT приостанавливает текущий Event до завершения указанной операции.

Поддерживаемые ожидания:

```text
DialogueCompleted
MovementCompleted
AnimationCompleted
EventCompleted
LocationTransitionCompleted
```

WAIT не является произвольным timer system.

Для MVP не требуется:

- произвольное ожидание N секунд;
- wait for arbitrary State;
- пользовательские asynchronous callbacks.

### 9.3. CALL

CALL запускает Event и ожидает его завершения.

```text
CALL event.morpheus_intro
```

После успешного completion вызывающий Event продолжает исполнение.

Если вызываемый Event Failed, ошибка передаётся вызывающему Event.

### 9.4. START

START запускает Event без ожидания.

```text
START event.background_reaction
```

START предназначен для ограниченного фонового исполнения.

Background Event не может START-ить Exclusive Event.

Exclusive Event может START-ить Background Event, если это не создаёт конфликтов.

### 9.5. END

END завершает Event успешно.

Event становится Completed.

---

## 10. Event Call Constraints

Для MVP:

- один Event не может вызвать самого себя;
- Event не может вызвать Event, который уже Running;
- повторный запрос запуска Running Event игнорируется;
- максимальная глубина CALL ограничена;
- максимальное количество автоматических Events в одной цепочке ограничено;
- Validator обнаруживает очевидные CALL cycles.

Полная математическая проверка всех runtime cycles не требуется.

### 10.1. CALL и Repeat Policy

CALL не обходится через Repeat Policy.

Если Event уже Completed и имеет `once`, повторный CALL не запускает его.

Scenario System сообщает caller о том, что вызов не состоялся.

Для MVP предлагается считать такой CALL ошибкой сценарной последовательности, если сценарист явно не проверил доступность Event заранее.

---

## 11. Error Handling

### 11.1. Event Errors

Примеры:

- invalid Action;
- State Mutation rejected;
- Dialogue unavailable;
- CALL failed;
- invalid Location Transition;
- WAIT target unavailable;
- Event execution limit exceeded.

### 11.2. Failure Policy

Если Action не может выполниться:

1. Event переходит в Failed.
2. Scenario System прекращает последовательность.
3. Scenario System освобождает Exclusive control.
4. Game Flow возвращает управление в безопасное состояние.
5. Ошибка записывается в diagnostics.

Не допускается продолжение Event после неожиданного Failure.

### 11.3. Recovery

Recovery — ответственность Game Flow.

Scenario System сообщает об ошибке и освобождает принадлежащие ей ресурсы управления.

Scenario System не пытается самостоятельно восстановить Unity Scene, Dialogue UI или Input.

---

## 12. Game Flow Integration

Scenario System не владеет глобальным input lock.

При запуске Exclusive Event Scenario System запрашивает control ownership у Game Flow.

Game Flow:

- определяет допустимость запуска;
- предоставляет control;
- блокирует нужные действия игрока;
- возвращает управление после завершения или ошибки.

Scenario System не должна самостоятельно управлять Unity Input System.

### 12.1. Event и Dialogue

Exclusive Event и Dialogue Mode — разные измерения.

Exclusive Event может:

- запускать Minimalistic Dialogue;
- запускать Visual Novel Dialogue;
- ожидать завершения Dialogue;
- продолжать выполнение после Dialogue.

Dialogue System не становится владельцем Scenario execution.

---

## 13. State Changed Integration

State System публикует State Changed после commit.

Scenario System:

1. получает notification;
2. определяет потенциально связанные Triggers;
3. проверяет Event eligibility;
4. вычисляет Launch Conditions;
5. запускает или ставит Event в очередь.

State Changed не означает автоматический запуск всех Events.

Trigger matching и Conditions должны ограничивать количество кандидатов.

---

## 14. Location Integration

Location Entered trigger возникает при обычном входе игрока в Location.

Не возникает при:

- Restore;
- визуальной реконструкции;
- повторной регистрации Unity representations;
- технической перезагрузке Location без сюжетного перехода.

Location Visit отслеживается Scenario System.

Location System сообщает о факте перехода, Scenario System определяет его сценарные последствия.

---

## 15. Dialogue Integration

Scenario System управляет Dialogue lifecycle:

```text
Start Dialogue
    ↓
WAIT DialogueCompleted
    ↓
Continue Event
```

Dialogue System:

- отображает реплики;
- обрабатывает click/Space;
- сообщает о завершении;
- не определяет дальнейший сценарий.

Dialogue completion notification не означает автоматического завершения Event.

---

## 16. Determinism

Scenario execution должен быть предсказуемым.

Для MVP:

- Actions исполняются последовательно;
- Event не имеет concurrent instances;
- Exclusive Events сериализованы;
- Background Events ограничены;
- Launch Conditions перепроверяются перед запуском;
- Restore не воспроизводит ordinary triggers;
- порядок queued Exclusive Events FIFO.

Не требуется deterministic simulation для физики, анимаций или Unity frame timing.

---

## 17. Validator

Validator проверяет:

- Event IDs;
- Trigger references;
- Condition references;
- Action definitions;
- CALL targets;
- START targets;
- CALL cycles;
- недостижимые Actions;
- отсутствующие END;
- некорректные WAIT targets;
- невозможные execution type combinations;
- Background Events, нарушающие ограничения;
- Repeat Policy;
- очевидные event conflicts;
- неизвестные fields;
- обязательные fields.

Validator не гарантирует обнаружение всех runtime deadlocks.

## 19. Out of Scope

Не вводить:

- arbitrary scripting language;
- priorities;
- event preemption;
- universal scheduler;
- concurrent Event instances;
- arbitrary timers;
- arbitrary asynchronous callbacks;
- general-purpose task graph;
- dynamic code execution;
- save/load active Event stack;
- save/load active Dialogue;
- universal rollback;
- automatic recovery of arbitrary failed scenarios.

---

## 20. Acceptance Criteria

Scenario System считается архитектурно реализованной, когда:

1. Triggers централизованно обрабатываются.
2. Events имеют стабильные IDs и Definitions.
3. Launch Conditions вычисляются через Condition System.
4. Event lifecycle корректен.
5. Repeat Policies соблюдаются.
6. Exclusive Events сериализованы.
7. Background Events ограничены.
8. Actions вызывают специализированные Gameplay Systems.
9. WAIT работает для предусмотренных операций.
10. CALL и START имеют корректную семантику.
11. Event failures приводят к безопасному освобождению control.
12. Game Flow владеет input permissions.
13. State Changed не запускает Events напрямую внутри State System.
14. Restore не воспроизводит ordinary triggers.
15. Validator обнаруживает очевидные Event errors и cycles.

---

## 21. Implementation Planning Boundary

Architecture 0.4 определяет поведение и ответственность Scenario System, но не фиксирует:

- C# class hierarchy;
- конкретные interfaces;
- Unity MonoBehaviour layout;
- runtime data structures;
- JSON Schema;
- implementation task ordering;
- implementation plan.

Эти решения должен предложить Claude Code при разработке implementation plan. Они должны соответствовать архитектурным инвариантам и пройти независимое ревью.
